## 6. Example End-to-End Workflow

Every workflow in the system should be documented at this level of detail — this is the reference example (tick to learning):

```
Market Tick
  → Market Intelligence
  → Feature Engine
  → Market Structure
  → Liquidity
  → Funding
  → News
  → Macro
  → Debate
  → Supervisor
  → Risk
  → Execution
  → Monitor
  → Reflection
  → Learning
  → Knowledge Graph
```

Every arrow above is an **event on the event bus**, not a direct function call — this keeps every stage independently testable, replaceable, and observable, per the Architecture Principles in Section 21.

### 6.1 Event-Driven Architecture Flow (Enhancement)
To ensure strict decoupling, the arrows above represent concrete events published to a message broker (e.g., Redis Pub/Sub, Kafka).

1. **`TICK_RECEIVED`**: Fired by Exchange Connector. Contains raw price/volume data.
2. **`FEATURES_COMPUTED`**: Fired by Feature Engine. Contains normalized data, RSI, MACD, etc.
3. **`SIGNAL_GENERATED`**: Fired by Market Intelligence. Payload: `{"strategy": "trend_follow", "direction": "long", "confidence": 0.85}`.
4. **`DEBATE_CONCLUDED`**: Fired by Supervisor AI after parsing signals and portfolio state.
5. **`TAR_SUBMITTED`**: Trade Authorization Request submitted to Risk Engine.
6. **`TAR_APPROVED` / `TAR_REJECTED`**: Fired by Risk Engine (CRO).
7. **`ORDER_ROUTED`**: Fired by Execution Engine upon API submission.
8. **`ORDER_FILLED`**: Fired by Execution Engine upon exchange confirmation.
9. **`REFLECTION_COMPLETED`**: Fired by Memory/Learning post-trade closure.

## 19. Execution Requirements

Execution must optimize for: slippage, latency, fees, partial fills, order splitting, exchange selection, retry policies, and **idempotency** (a retried order must never result in a duplicate fill).

### Execution Optimization Logic (Enhancement)
1. **Idempotency:** Every `POST` to the exchange must include a `Client_Order_ID` generated by the Execution Engine. If a timeout occurs, the Engine retries using the *same* ID. The exchange will reject it if it was already filled, preventing double-spending.
2. **Order Splitting:** If `order_size` > 2% of the 5-minute average volume, the Execution Engine automatically overrides "MARKET" orders and defaults to a TWAP (Time-Weighted Average Price) execution over 15 minutes.
3. **Slippage Circuit Breaker:** If slippage on a market order > 0.5% (50 bps), halt execution of the remaining split chunks and request a new TAR from the Supervisor.
